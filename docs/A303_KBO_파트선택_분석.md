## 2. A — 코어 게임 서버

**범위**: 판 상태 머신 + 스케줄러 / 투표 집계(동점·영향력·동시성) / 포인트 원장 / 채점(Brier)

### 장점

**① 포인트 원장이 토스뱅크 Customer Asset 그 자체다** ⭐⭐⭐

설계지도에 이렇게 적혀 있다.

> "포인트는 잔액 컬럼이 아니라 point_ledger에 **append-only로 쌓아 온체인 에스크로와 1:1 대응**시킨다."

이건 내가 지원서에 쓴 것과 정확히 같은 사고다 — "자산 값이 깨져도 로그에서 다시 계산할 수 있어야 한다".
**그런데 나는 그걸 말만 했지 설계한 적이 없다.** 여기서 실제로 만들면 말이 경험이 된다.

> 면접에서: "잔액을 컬럼으로 두면 그 값이 틀렸을 때 복구할 근거가 없습니다. 그래서 append-only 장부로 쌓고 잔액은 파생으로 계산했습니다. 외부 기록(온체인 에스크로)과 1:1로 대조할 수 있게 `ref_type`/`ref_id`를 남겼습니다."

**② 실험으로만 해본 RDB 동시성을 서비스에 적용한다** ⭐⭐⭐

마감 순간에 투표가 몰린다 = 정각복권과 같은 구조. **그런데 이번엔 MySQL이다.**

> ⚠️ **정정**: 이 문서 초판에 "RDB 동시성을 써본 적이 없다"고 적었는데 사실과 다르다.
> 선착순 쿠폰 재고 차감을 대상으로 **nGrinder 부하 테스트로 4가지를 비교 측정한 기록이 노션에 있다**
> (락 없음 / 비관적 락 / 원자적 UPDATE / 배칭+CompletableFuture).
> 다만 **개인 노트북 로컬 환경의 학습 실험이고 실제 서비스에 적용한 적은 없다.**
>
> 그래서 논거가 약해지는 게 아니라 **바뀐다.** 비교는 해봤으니 "무엇이 왜 빠른지"는 안다.
> 없는 건 **그 판단을 실제 서비스 제약 아래에서 내려본 경험**이다. A가 정확히 그 자리다.

여기서 쓰면 다음을 실경험으로 말할 수 있다.

| 도구 | 어디에 쓰나 |
|---|---|
| `UNIQUE(problem_id, user_id, direction_id)` | 같은 사람이 같은 방향에 두 번 투표 못 하게 |
| `UNIQUE(tx_hash)` | 체인 영수증 중복 반영 차단 (= 멱등) |
| `SELECT ... FOR UPDATE` | 마감 시점 집계 스냅샷 |
| `@Version` | 판 상태 전이 경쟁 (두 스케줄러가 같은 판을 전이시키면?) |

**실험실에서 순위를 재본 것과, 서비스 제약 아래에서 하나를 고르는 것은 다르다.** 후자가 A의 수확이다.

**③ 상태 머신 + 마감 스케줄러 = 내가 겪은 사고의 재발 방지판** ⭐⭐

설계지도가 직접 말한다.
> "판 하나에 마감 이벤트가 7~9번 — **스케줄러와 전이 검증이 서비스 품질을 결정한다**"

이건 미니앱 큐 리전 사고와 같은 위험이다. **마감이 안 돌면 판이 영구히 멈춘다.**
그때 배운 것을 **처음부터** 넣을 수 있다.

- 안전망(주기 스캔으로 "마감 시각이 지났는데 아직 전이 안 된 판" 찾기)
- **안전망이 발동한 횟수를 지표로** ← 큐 리전 사고의 결론
- 전이 실패를 로그가 아니라 카운터로

> 면접에서: "미니앱에서 안전망이 고장을 숨겨서 발견이 늦어진 적이 있습니다. 그래서 이번엔 안전망을 두되 **안전망이 실제로 일한 횟수를 지표로** 만들었습니다."

**④ 상태 전이 규칙 = JD "도메인 모델링" 요건 강화** ⭐⭐

여기어때 JD, 토스, SKT 다 도메인 모델링을 본다. A302에서 한 것을 **한 단계 큰 규모로** 반복한다.
9개 상태 + 무효 분기 + "이 상태에서 허용되는 요청인가" 검사는 **A302보다 명백히 어렵다.**

**⑤ Brier score — 수학과 전공이 처음으로 쓸모를 갖는다** ⭐

지금까지 수학과 배경이 이력서에서 아무 역할을 못 했다.
채점 로직(Brier + 기준선 비교 + 헛스윙 판정)은 **확률 채점 규칙**이라 전공과 연결된다.

> "확률 예측을 채점하려면 맞았다/틀렸다가 아니라 **얼마나 자신 있게 틀렸는지**를 재야 합니다. Brier score가 그걸 하고, 기준선과 비교해야 의미가 생깁니다."

### 단점

**① 도메인이 특수해서 설명 비용이 든다**
"예측 배틀 채점"은 면접에서 배경 설명이 필요하다. 반면 "외부 시스템 연동"은 한 문장이면 통한다.
→ **대응: 이력서에는 "게임"이 아니라 "원장·상태 머신·마감 스케줄러"로 쓴다.** 도메인을 지우고 구조만 남긴다.

**② 코딩량이 많다**
상태 9개 × 전이 검증 + 집계 + 원장 + 채점. B보다 순수 구현량이 클 가능성이 높다.

**③ 블록체인을 못 만진다**
이력서 희소성으로는 손해. 다만 **내 지원 방향(백엔드 정합성)과는 축이 다르다.**

## 3. B — 인테그레이션

**범위**: 체인 연동(영수증 검증·멱등·부분 실패 복구) / AI 서버 연동(타임아웃·재시도·스냅샷) / KBO 수집기 / 컨트랙트 인터페이스

### 장점

**① 여기어때 채널연동 JD와 가장 직결된다** ⭐⭐⭐
"외부 시스템과 연동하고 실패를 다룬다"가 그 직무 자체다.

**② 블록체인 경험은 희소하다** ⭐⭐
지원자 대부분이 없다. 다만 **핀테크·커머스 백엔드 채용에서 가점 요인인지는 회사마다 다르다.**

**③ 부분 실패 복구가 진짜 어려운 문제다** ⭐⭐
"TX는 체인에 올라갔는데 우리 DB 반영이 실패" = ACK 레이스의 상위 호환. 난이도는 확실히 높다.

### 단점 — 이게 결정적이다

**① 이미 가진 카드와 겹친다** ⚠️⚠️⚠️

| B에서 할 일 | 내가 이미 가진 카드 |
|---|---|
| AI 서버 연동 (타임아웃·재시도) | **A302에서 똑같이 했다.** 회로차단기까지 |
| 체인 영수증 검증 + 멱등 | 환전 멱등키 2단계와 같은 구조 |
| 외부 전송과 DB 기록의 순서 | ACK 레이스와 같은 구조 |
| KBO 데이터 수집기 | 텔레메트리 수집과 유사 |
| 컨트랙트 인터페이스 관리 | **API 계약서 4종과 같다** |

**네 항목 중 네 개가 이미 있는 카드다.** 더 잘할 수는 있어도 **새 영역이 안 열린다.**

면접관 입장에서 "외부 연동 사례 3건"과 "4건"의 차이는 거의 없다.
반면 "정합성 원장 설계"가 있느냐 없느냐는 차이가 크다.

**② AI 서버 연동은 A302의 반복이다**
FastAPI 호출 + 타임아웃 + 재시도 = GPU 서버 검증 호출과 사실상 같다.
**"또 했습니다"는 성장 서사가 안 된다.**

**③ 블록체인이 취업 방향과 어긋날 수 있다**
지금 지원 방향이 토스뱅크 자산 정합성 / 여기어때 채널연동 / SKT BSS다.
**셋 다 블록체인을 안 쓴다.** 이력서 한 줄로는 좋지만 **깊게 파는 시간 대비 회수가 낮다.**

## 5. A를 맡되 반드시 챙길 것

### 5-1. 경계 세 지점의 계약은 내가 주도한다

설계지도는 "A는 바깥과 통신 안 하고, B는 게임 규칙 몰라도 된다"고 했지만 **실제로는 세 곳이 겹친다.**

```
① 체인 영수증 검증(B) ──→ 포인트 원장 반영(A)
   누가 멱등을 보장하나?  tx_hash UNIQUE는 A의 테이블(point_ledger)에 있다

② AI 실행 실패(B) ──→ 판을 무효로 전이(A)
   실패 판정 기준은 누가 정하나? 재시도 몇 번 후 포기인가?

③ 마감 시각(A) ←→ 데이터 스냅샷 확정(B)
   스냅샷이 마감보다 늦으면 세 에이전트 조건이 달라진다. 순서 보장은?
```

**이걸 도메인 이벤트 계약으로 먼저 정의한다.**
A302에서 계약서 4종을 만든 경험을 그대로 쓴다. 그리고 이건 **A를 맡아도 B의 절반을 이해하게 되는 길**이다.

> 이력서에 쓸 때: "A/B 경계에서 멱등 책임이 모호했던 지점을 계약으로 고정했습니다."

### 5-2. 처음부터 넣을 것 — 겪은 사고의 재발 방지

| 장치 | 어느 사고에서 배운 것인가 |
|---|---|
| `UNIQUE(tx_hash)` on point_ledger | 환전 멱등 (제안만 했던 것을 이번엔 구현) |
| **안전망 스캔 + 안전망 발동 횟수 지표** | 큐 리전 (안전망이 고장을 숨김) |
| 상태 전이를 엔티티가 검증 | A302 상태 전이 규칙 |
| 전이 실패를 로그가 아니라 카운터로 | "로그는 사람이 볼 때만 작동한다" |
| 마감 시각 지연 p95 지표 | 증상 기반 지표 우선 원칙 |

**이게 성장 서사가 된다.** "겪었고, 다음 프로젝트에서 처음부터 넣었다"는 신입에게 가장 강한 스토리다.

### 5-3. 이력서에 쓸 때 도메인을 지운다

| ✕ 게임 언어 | ○ 구조 언어 |
|---|---|
| 예측 배틀 판 상태 관리 | **9단계 상태 머신과 마감 스케줄러 설계** |
| 포인트 투표 집계 | **마감 시점 동시 쓰기 집계, 유니크 제약과 락으로 중복 차단** |
| 포인트 원장 | **append-only 자산 원장 — 잔액을 파생으로 계산해 외부 기록과 대조 가능하게** |
| Brier 채점 | 확률 예측 채점과 기준선 비교 |

## 6. ⚠️ 예상 반론 두 개

**"여기어때는 채널연동인데 B가 맞지 않나?"**

맞다. **단일 지원처만 보면 B다.**
하지만 이미 외부 연동 카드가 3장이라 **4장째의 한계 효용이 낮다.** 그리고 여기어때 면접에서도 결국 오버부킹(동시성)과 정합성을 묻는다 — **거기엔 A가 더 강하다.**

**"블록체인 경험이 아깝지 않나?"**

아깝다. 다만 **지금 지원하는 세 곳 다 블록체인을 안 쓴다.**
그리고 설계지도에 "셋 다 SSAFY Sub PJT에서 이미 만들어본 구조의 재사용"이라고 되어 있다 —
**이미 한 번 해본 것이면 희소성 주장의 근거는 그것으로도 남는다.**

## 7. 확인해야 할 것

- **팀원이 어느 쪽을 원하는지.** 둘 다 A를 원하면 협상 필요
- **기간.** 짧으면 A의 구현량이 부담이 될 수 있다
- **컨트랙트 담당자가 따로 있는지.** 설계지도에 "컨트랙트 담당자와의 인터페이스"라고 되어 있어 별도 인력이 있는 듯하다
- 3단계 개발 순서(mock → 실연결 → 체인)에서 **1단계는 사실상 A의 일**이다. 시작 부담이 A에 몰린다
